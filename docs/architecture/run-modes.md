# Run modes, server, and job runner

## Local vs Databricks App

The same codebase runs two ways, selected by environment:

- **Local:** `python app.py`. `app.py` puts `src/` on `sys.path` (so `main.py`'s flat imports resolve) and calls `main()`. The server binds `0.0.0.0:<incident_input.port>` (default 5000). Auth uses `DATABRICKS_HOST` + `DATABRICKS_TOKEN` (a PAT) or a `~/.databrickscfg` profile, resolved by `databricks-sdk`. Local env (tokens, `HF_HUB_OFFLINE=1`) lives in the gitignored `.afir_env`; the verified launch line is:

  ```bash
  set -a; source .afir_env; set +a; DATABRICKS_APP_PORT=8137 python app.py
  ```

  **`source .afir_env` is load-bearing, and skipping it fails late.** Without it `DATABRICKS_TOKEN` is empty, so every LLM stage 401s (`Credential was not sent or was of an unsupported type`) — the whole pipeline, since six of nine stages are LLM calls. Startup therefore logs a single `NO LLM CREDENTIAL: env var X is empty…` **ERROR** when the static `api_key_env` path resolves nothing; it stays non-fatal (an operator may boot the server before exporting the token) but the app must not look healthy when no call can succeed. It previously logged one INFO line — *"the LLM client will fail on first call"* — among ~30 skipped-source lines, then reported `ready`, so the failure surfaced only after an incident was submitted and understanding had run. Relatedly, a 401/403 is an `LLMCredentialError` (a `NonRetryableError`): retrying a credential the endpoint refuses is pointless, and left retryable one empty env var produced **nine** 401s per stage (3 `structured_output` attempts × 3 stage attempts, plus a wasted JSON-fallback call each) that buried the one actionable fact. The message names the remedy — which env var is empty, or that a set-but-refused PAT is likely expired or workspace-scoped to a different workspace than `base_url`.

  With the embedding model present in `model_cache/all-mpnet-base-v2` (mirrored into the HF hub cache) and `HF_HUB_OFFLINE=1`, RAG boots with **real embeddings** — logs `EnhancedRAG ready with N documents` on `mps`. The model cannot be downloaded on this machine at runtime (self-signed cert in the chain → `SSLCertVerificationError` against huggingface.co). If it is ever absent, the orchestrator degrades to `PlaybookFallback active with N playbook documents` and the pipeline still runs.
- **Databricks App:** declared via `app.yaml` (`command: ["python", "app.py"]`). The platform injects `DATABRICKS_APP_PORT` (the server binds it instead of the config port) and OAuth service-principal vars (`DATABRICKS_HOST`/`DATABRICKS_CLIENT_ID`/`DATABRICKS_CLIENT_SECRET`) — no token needed. The App's service principal needs `CAN USE` on the SQL warehouse, `CAN QUERY` on the serving endpoint, and `SELECT` on the catalog. `AFIR_CONFIG_DIR`/`AFIR_DATA_DIR` (set in `app.yaml`) point config + writable artifacts at deploy-friendly paths.

## One aiohttp app, one port

The server is a **single aiohttp app** on one port. Two ways to run an incident:

- **Classic blocking endpoints** (`/api/v1/incidents`, `/api/v1/ir`, `/api/v1/incidents/freetext`): run the full pipeline and return the report as JSON in one response. These run *over the job machinery* via `process_incident_via_job` (create an AUTO job, run all stages, return `outputs["report"]`) — same code path as the controllable jobs, just awaited to completion.
- **Controllable jobs** (`POST /api/v1/jobs` `{description, mode}`): launch a `Job` that runs the same nine stages one at a time under a `JobManager`, streaming progress and accepting control. `mode` is one of `auto` / `semi_auto` / `supervised` / `step` — the last three all stop the run, but `step` pauses *before* a stage while the two gate modes wait *after* one, on its output (see `hitl.md` §3). `GET /api/v1/jobs/{id}` (snapshot), `GET /api/v1/jobs/{id}/events` (**SSE** stream — `text/event-stream` on the shared port; no second websocket server), `POST /api/v1/jobs/{id}/control` `{action}` (pause/resume/step/cancel_stage/cancel_all/retry_stage/retry_all/skip_stage), `POST /api/v1/jobs/{id}/gate` + `GET /api/v1/gates` (approve/reject/override; the cross-job inbox), `POST /api/v1/jobs/{id}/outputs/{stage}` (override one stage's result), `GET /api/v1/jobs/{id}/export` + `POST /api/v1/jobs/import` (study/reload).

`POST /api/v1/feedback` feeds the `FeedbackLoop`. There is no background queue loop (removed in Phase 6 — Apps allow one port).

**Jobs are no longer only in memory.** A gate holds indefinitely, so `main()` restores persisted jobs before the server starts and re-arms their gates once the loop is running; an in-flight job comes back as `PAUSED`, never silently re-running a stage whose side effects are unknown. See `hitl.md` §4.

**Logging format is selectable** (`logging.format: console|json`, or `AFIR_LOG_FORMAT`). In a Databricks App the console is the only telemetry that leaves the container, so `json` makes the stage/gate/health lines queryable — the message text is identical either way, with structured fields carried on `extra=` rather than scraped from the prose (`src/utils/logging_setup.py`).

## Console UI + full API parity

`GET /` serves a single-page console — one inline HTML document, vanilla JS, **no bundler and no CDN** (it must work offline inside a Databricks App). `src/webui.py` is now only the assembly point: `INDEX_HTML = build_index_html()`, built once at import, with the page itself split across `src/ui/*` (see that package's docstring for the module layout — `theme` / `shell` / `panels` / `report` / `config` / `script_core` / `script_tabs` / `script`).

**Light and dark, one token name per meaning.** Every colour is a CSS custom property declared exactly twice — once under `[data-theme="dark"]`, once under `[data-theme="light"]` — and **nowhere else**; `tests/test_webui.py` asserts both blocks define the same key set and that no `#hex` or `rgba()` survives outside them, because a literal in a component rule is a value that is right in at most one mode (that is how both sticky bars were dark grey over white). The five semantic status tokens (`--ok`/`--running`/`--warn`/`--err`/`--skip`) change *value* between modes and never *meaning*: amber is "a human is needed" on a badge, a health bar, the gate and a log line alike.

The theme is chosen by an **attribute on `<html>`**, not by `@media`, so a stored preference can override the OS. It is tri-state — dark / light / auto — and **"auto" is the absence of `localStorage["afir-theme"]`** rather than a third stored value, which is what stops it drifting out of step with an OS that changes underneath it. **The one new trap:** setting the attribute before first paint needs a script in `<head>`, and `test_webui.py` extracts the page's JS by splitting on the literal `"<script>"` — so a plainly spelled one there makes `JS` resolve to the boot block and silences ~90 assertions *while still passing*. It is therefore spelled **`<script data-boot>`**, and `test_the_extracted_js_is_the_main_script_not_the_boot_script` pins that. The boot block duplicates ~6 lines of `applyTheme` deliberately: it cannot call into the main script (which loads at the end of `<body>`) and the main script must not call into it, since anything defined only there is invisible to the declaration scan.

**Navigation is a vertical rail**, not a horizontal tab strip: `260px` expanded, `64px` icons-only collapsed, persisted in `localStorage["afir-rail"]` (one of four keys — see `afir-job` / `afir-tab` below), an overlay drawer over a scrim below 760px. The three states are deliberate — a window resize is not a preference, so `toggleRail` persists only on the wide branch. Level 1 is the five sections and keeps `id="tabnav"` + `data-tab`; **level 2 uses `data-for`/`data-sub`**, because `test_every_tab_has_a_nav_button_and_a_view` asserts the `data-tab` set is *exactly* the five and a sub-item spelled that way would join them and demand a `#view-` of its own.

Level 2 has **two kinds**, and conflating them is how a highlighted rail item ends up pointing at a hidden panel: an **anchor** scrolls to a panel that is always present (Investigate, Monitor, Report), a **view** switches which panel exists at all and routes through the radio group that already owns that choice (`setConfigView` / `setKnowledgeView`). Both the rail's level-2 items **and** the in-content `.seg` strips are kept — the collapsed rail hides level 2, leaving the strip as the only sub-navigation on screen — so exactly one function, `setView(tab, sub)`, writes both and they cannot disagree.

**Sticky offsets are derived, never typed.** `--topbar-h` is the single source of the header's height; the report contents list, the config nav and `.panel { scroll-margin-top }` are all calculated off it. Opening a gate makes the header taller, so `setGateStrip` writes `data-gate="open"` on `<html>` and the stylesheet redeclares the token for that state — one attribute, no measurement. The `scroll-margin-top` half fixes a latent bug: four existing `scrollIntoView({block:"start"})` calls were landing their target *underneath* the sticky topbar. And every scroll on the page goes through `scrollToEl`, because a `behavior:"smooth"` passed in JS is **not** overridable from CSS and `prefers-reduced-motion` has to be read where the call is made.

Icons are an inline SVG `<symbol>` sprite with `stroke: currentColor`, replacing 31 Unicode glyphs that rendered differently per platform (several are missing from common Windows font stacks). `currentColor` is the point: an icon in a danger button, a warn badge or a muted rail item takes its container's state colour with no per-icon override.

**Five tabs**, plus two panels that stay visible on every one of them:

| Tab | What it does |
|---|---|
| **Investigate** | submit an incident, pick the run mode, tick **extended retrieval**, 9 expandable phase cards with per-phase live timers, the control toolbar, and per-stage detail renderers (understanding's downstream impact, per-source log bars + sample rows, correlation's resolved/discovered keys, anomaly confidence bars) |
| **Monitor** | the event console in **two modes** — *basic* (a lifecycle allowlist: stage/job/gate/intervention events, the shape an operator watches a run through) and *advanced* (every event, every scalar inline, every structure as JSON), plus text filter, type filter, and an NDJSON download of the whole buffer |
| **Report** | a **recent-runs** list, then the finished report rendered from `?format=view` with a generated table of contents, and one-click `md` / `pdf` / `html` / `json` export + `raw` / `transformed` evidence download, each button enabled from the `/artifacts` inventory so it is only offered when the file exists |
| **Configuration** | every key in `config/*.yaml`, typed per field (`number`/`integer`/`boolean`/`string`/`choice`/`text`), tagged `live` or `restart`, plus a raw YAML editor and a file importer |
| **Knowledge** | the pack editor: a file tree per installed pack with an inline editor, pack-wide diagnostics, snapshot history + restore, scaffold/import, and the AI assistant's propose → diff → apply/edit/reject panel. Five sub-views (`files` / `check` / `history` / `io` / `assist`) behind one `.seg` group |

The gate decision panel, the two topbar popovers and the toast stack live at **global** scope rather than inside a tab, because a gate opens while the operator may be reading a report or editing config and it holds the run until answered — and the popovers' triggers sit in the topbar, which is visible from every tab. It stays **in the flow rather than becoming a modal**: the job at a gate is to read the stage output before deciding (that is what *Inspect output* is for), and a dialog that must be dismissed to see the evidence turns a review into a guess — a gate holds indefinitely, so there is no time pressure a modal would serve. Instead there are **three signals in ascending intrusiveness**: the rail's `#navGates` count (visible on every section, collapsed rail included), a topbar gate strip (`role="status" aria-live="polite"`) naming the stage with a *Review* button, and the amber panel itself. The strip and the count answer *different* questions — "this run needs you" vs "how many decisions are queued anywhere" — so they are computed separately; merging them would either double-count or hide another job's gate. The rest of the HITL surface sits with them: the mode selector, per-stage health badges, the score bar with every reason, approve/reject/override, the mid-run stage-output override editor, and the intervention/decision trail.

**Jobs and Run controls are popovers, not panels in the flow** (`#jobsPop` / `#ctlPop`), opened from `#jobsToggle` and the job chip. As full-width `.panel`s they cost page height permanently: Jobs shoved the stage cards down the viewport, and Run controls held a row for buttons that are disabled without an attached job. Their bodies moved **verbatim** with every id unchanged, because `ctlEnabled()` and `resolveGate("override")` address them by id and `test_control_buttons_are_actions_the_runner_accepts` scans the `data-act` values. Four things the primitive owns, each the half that rots if left out: position derived from `var(--topbar-h)` (a gate opening *redefines* it, so a hardcoded offset tucks the panel under the bar); **one** `openPop`/`closePop` pair rather than three implementations; focus in on open, skipping `.popicon` so it lands on the first real control; and focus **return** on close, guarded by "was focus inside" — `[hidden]` is `display:none`, so closing on Escape without it drops a keyboard user to the body, while doing it unguarded steals focus on every outside click, since `closeAllPops()` runs on all of them. `<dialog>` + `showModal()` is the wrong tool: it makes the rest of the page inert, and a gate can open while the jobs list is up. `SUBVIEWS` grew a third kind (`kind:"pop"`) so the rail's *Run controls* item still leads somewhere real; with no job attached it writes to `#status` instead of opening an inert panel anchored to a hidden chip.

**Run controls also hold the retrieval-plan editor** (`#qpPanel`, loaded on demand by `#qpLoad`): the queries this run planned, each removable, plus a menu of the sources no query targets, ordered with the adjudicating procedure's own unmet dependencies first. It is the operator half of a reported-not-injected dependency (`hitl.md` §2b, `docs/API.md` §5c). Two rules it keeps for reasons the page cannot re-derive: the client sends only `source` + `question` and the server builds every query, because which entities a source can bind is pack knowledge and a second copy of it in JS would be a second answer; and `ctlEnabled(false)` **clears** `qpPlan`/`qpDrop`/`qpAdds`, since staged edits are indices into one job's query list and carrying them across an attach would apply them to another run.

**Two more `localStorage` keys, and the attach bug they exposed.** `afir-job` and `afir-tab` join `afir-theme` / `afir-rail`, written in the same try/catch style, so a refresh re-attaches instead of dropping a live investigation. `attachTo` owns both sides — `rememberJob` once the snapshot is in hand, `forgetJob` on any failure — so a job pruned by `_JOB_TTL_SECONDS` degrades to a clean page rather than a stuck chip. Restoring it surfaced the real defect: `attachTo` used to `fetchResult()` for a terminal job and `subscribe()` only otherwise, so opening a **finished** job from the jobs list cleared the console and never subscribed — an empty Monitor for a run whose whole history the server was holding. It now **always** subscribes (`JobManager.subscribe` replays `_event_history` before tailing), and an `attachedAt` stamp marks replayed events to skip `pushTrail` **only**: logging, badges and the by-source table still run, because the snapshot's `interventions` + `gate_history` are already the complete trail and would otherwise double. Replay can only ever be a *suffix* of the history — the 500-event cap drops the oldest first — so it cannot downgrade a badge the snapshot restored. The clock reads `created_at`, and freezes at `updated_at - created_at` for a terminal job instead of ticking from zero.

**Re-attaching must restore what the run cannot be re-derived from the page, and a replayed event must not be mistaken for a live one.** Both bugs presented as "the refresh loses things", and they have separate causes:

- **The stage timer.** `handleEvent`'s `stage_started` branch stamped `Date.now()` unconditionally, so every attach and every refresh restarted the counter at zero — overwriting, a moment later, the very `started_at` the snapshot restores. It now reads the event's own `m.ts` (`Date.parse`, falling back to `Date.now()` only when absent, which is a genuinely live event where the two are the same instant).
- **The launch settings.** `Job.snapshot()` now carries `description` and `extended_retrieval`, and `attachTo` writes both back into the form. Neither is inferable by looking at the page, and the checkbox is the one that matters: a box reading *off* while the run behind it uses the extended budget misreports the run's own settings. The stage records the **effective** budget (`ctx.incident["extended_retrieval"] = True` when a run is extended by global config, not just per-incident), so a globally-extended run doesn't report itself as normal.

**The motion layer is short and reversible.** A `viewin` cross-fade on `.tabview` (free: `[hidden] { display: none }` means showing a view re-enters layout), `popin` on the popovers, a one-shot `cardflash` when a stage card changes state, and `:active` depression on buttons. Nothing exceeds 500ms, all of it is named in the `prefers-reduced-motion` block, and **no new JS-supplied `behavior:"smooth"`** — every scroll still goes through `scrollToEl`, which `_CODE.count("scrollIntoView") == 1` pins. The flash is suppressed while `restoring` is set (around the snapshot loop and for replayed events): motion asserting that something *just happened* is a lie about a run that finished an hour ago. Toasts carry transient outcomes a statusline nobody is looking at would swallow — capped at 3, auto-dismissed, `aria-live="polite"` — under one rule: **a toast is never the only record**, since a message that vanishes cannot be an audit surface.

**Four capabilities the API had and the UI did not**, each shipped with its assertion: `extended_retrieval` on launch (a slow source and an empty source fail identically — 0 rows, every decisive condition `unknown` — so raising the caps has to be *askable*); a **recent-runs** list merging live jobs with finished reports on disk (`GET /api/v1/incidents`, whose ids go back through `_safe_id` and are **dropped** if they fail, never sanitised); **job import** beside the existing export, closing a round trip that was half-built; and a **service indicator** reading `GET /health?deep=1` — bare `/health` stays byte-identical for the platform probe, and the deep answer distinguishes `None` (nothing wired, legitimate in tests) from `False` (wired and unusable), because an empty LLM credential 401s all six LLM stages while saying so only in a container log the operator cannot read.

**Accessibility.** `.seg input { display: none }` is gone: `display:none` removes the radio from the accessibility tree *and* the tab order, which had silently un-keyboarded **all six** segmented groups — including the run-mode selector, the only way to ask for a `supervised` run. They are now off-screen-but-focusable with the ring drawn on the label, which is also what makes the theme toggle three real radios with no custom ARIA to keep in sync. `:focus-visible` covers every interactive element (previously only three input types drew a ring), and `prefers-reduced-motion` disables the gate pulse, the brand pulse and every smooth scroll — safe precisely *because* the gate has three signals rather than one animation.

**Two client-side invariants** the modules depend on. Braces in the HTML/JS are literal, so the UI constants are **concatenated, never `.format`ted or f-stringed**. And concatenation order is the only dependency mechanism: function *declarations* hoist (so `script_core` may call into `script_tabs`), but `let`/`const` do not — which is why the single init block is last. UI functions must therefore be declarations, not anonymous handler closures, or `tests/test_webui.py`'s scan won't see them.

**Configuration is editable through the API and the UI** (§10 of `docs/API.md`). Two things make that safe enough to ship without auth on the port: literal secret values are redacted in both the structured read and the raw text (so they never leave the server, and the editable form offers `api_key_env`, never `api_key`), and a patch is all-or-nothing with `live` fields re-read into the running config while everything else is reported as `restart_required` rather than presented as applied. A `.bak` is kept on every whole-file write (gitignored — it holds real credentials). The patch is line-by-line text: comments survive, and nothing is ever **appended at EOF** — a duplicate key's winner would be parser-defined, so an absent key goes through `plan_insert` into its own section instead.

**A dotted path resolves to a DIRECT child at every segment, and the near miss reported success.** `_find_scalar_line` walks `a.b.c` by indentation, and its depth check used to accept a same-named key nested *arbitrarily deep* inside the parent. So editing the global `log_sources.max_results` wrote `log_sources.backends.elasticsearch.<cluster>.max_results` — the first `max_results` it met anywhere under `log_sources`, eight spaces in — and answered `applied`. That is the worst class of config bug: the operator's number is on disk, on the wrong key, with the UI agreeing it worked. Each level now **learns its child indent** from the first key seen inside the parent block and skips anything deeper. The guarantee has three tests: a fixture with two nested clusters each pinning the same key (the global must insert at indent 2 and neither cluster may move), a 4-space-indented file (the rule must be *learned*, not hardcoded to 2), and a sweep asserting **every** editable `main_config` field resolves to its own key in the shipped template.

**The Knowledge tab is the pack side of that same story**, and its constraints differ from the config tab's in two ways worth knowing before touching it. A file over 256 KB renders **read-only with a download button** — three generated schema files in an installed pack are ~456 KB, and a textarea round trip is how one gets lost. And `encodeURIComponent` must **never** appear in the pack segment of a `fetch`'s first argument: measured, `fetch("/api/v1/knowledge/"+encodeURIComponent(pack)+"/file")` extracts as `/api/v1/knowledge/{}`, which is truncated yet still matches a real route — so `test_every_fetch_url_is_a_registered_route` **passes vacuously while the button 404s**. Encode once when the pack is selected, then interpolate the bare variable. See `docs/architecture/knowledge.md` ("Editing a pack") and `docs/API.md` §11.

**Everything the UI shows is available over the API** (see `docs/API.md`): stages emit `stage_started` (with `started_at`), `stage_output` (with a compact `summary` — built by `summarize_stage()` in `pipeline_runner.py`, one `_summ_*` extractor per stage, defensive — plus `health`), `stage_completed`/`stage_failed` (with `duration_ms`), `source_progress`, and the gate events (`gate_opened`/`gate_resolved`/`gate_timeout`). The `GET /api/v1/jobs/{id}` snapshot carries per-stage `duration_ms`+`summary`+`health` and the job's `open_gate`/`pending_gate`/`gate_history`/`interventions`; `GET /api/v1/jobs` lists all live jobs; the classic blocking endpoints accept `?verbose=1` to return `job_id`+`stages`+`events` alongside the report (default body `{incident_id, report}` unchanged). The event log line also gets a `| duration_ms=… summary={…keys…}` digest. `WebhookDispatcher` pushes the six events an external system acts on, for integrators that cannot hold an SSE connection for the days a gate may wait.

**Three test files cover the UI, and each catches something the others cannot:**

- `tests/test_webui.py` — the type-checker this bundler-less page otherwise lacks. Every referenced DOM id exists, no call reaches an undefined function, every `fetch` URL is a registered route (URL helpers like `reportBase()` are inlined and query strings stripped first, or six endpoints go unchecked), and the JS/Python shared vocabularies agree — stage names, gate actions vs. what `JobManager.control` accepts, config field kinds, report formats, evidence kinds. **Add a control here, add its assertion there.** It also holds the invariants nothing else could catch: that the extracted `JS` is the main script and not the boot block, that both theme blocks define the same tokens and no colour literal escapes them, that every `SUBVIEWS` entry has both a rail item and a real target, that `.seg input` stays focusable, and that no sticky offset is a magic number. Two of those are *guards on the tests themselves*, which is why they earn their place.
- `tests/test_ui_server.py` — the server modules (`config_store.py`, `report_delivery.py`): that `describe()` never emits a literal secret (nested backend tokens included) while `${VAR}` survives, that a redacted export can't be re-imported, that the patcher keeps comments and never duplicates a key, that a traversal-shaped incident id is **rejected** rather than sanitised, and that `list_incidents` applies the same rule in the other direction — an id recovered from a *filename* is dropped, not sanitised into some other incident's id.
- `tests/test_ui_wiring.py` — the live contract, driving the real interface + `JobManager` over a `TestServer`: the SSE stream really emits every type basic mode filters on, `health` lives inside `stages[]` (an earlier build read a non-existent `snap.stage_health`), a rejection re-gates the same stage, and the override editor's `/export` → `POST /outputs/{stage}` → `skip_stage` round trip works on real payloads. Note the interface builds its rate limiter in `start_server()`, which `TestServer` bypasses — assign one or every handler raises `AttributeError`.

## Job runner

`src/pipeline_runner.py` (flat imports): `JobManager` drives a fixed `build_stage_descriptors()` list (nine `StageDescriptor`s that mirror `process_incident`'s body 1:1, reading inputs from `JobContext.outputs` so a stage can retry standalone). The stage-runner loop enforces pause boundaries (`Job._pause_event`), STEP-mode advance (`_step_event`), and cancellation.

**Cancel is a race, not a task-cancel-and-wait:** a stage is run as a task *and* awaited against `Job._cancel_event` via `asyncio.wait(FIRST_COMPLETED)` — so cancel terminates the job immediately even when the underlying call swallows `CancelledError` (the OpenAI SDK internally retries requests and won't unwind promptly); the orphaned call finishes in the background and is discarded.

Jobs are in-memory (`_jobs` dict) with TTL pruning of terminal jobs on `create_job`; `export_job`/`import_job` serialize `outputs` via per-key `_OUTPUT_CODECS` (Pydantic `model_dump`/`model_validate`, base64 for a bytes report). Events fan out through `notifications.EventEmitter` (`emitter.emit(...)`) to the logger **and** each job's `_event_history` (replay buffer) + live `_subscriber_queues`; `send_notification(incident_id, status, message)` is a backward-compatible shim over it.

`process_incident(incident, modules)` keeps its exact signature/behavior (mocked in `test_main.py`) — only the whole-pipeline `@async_retry_with_backoff` was removed (stage-level retry replaces it). `notifications.py` and `pipeline_runner.py` use flat imports; `incident_input.py` passes a plain string mode (`"auto"`/`"step"`) so it needs no cross-import of the `JobRunMode` enum (avoids the dual-import identity trap).

### The run queue: a backlog that drains, and a backlog that is visible

A run costs ~38 minutes at the median and fans out ~19 retrievers, each making two or three LLM calls against **one** shared concurrency semaphore and one rate limiter. So launching twenty submitted incidents at once does not make the backlog finish sooner — it makes every run in it slower, and the queue that decides the order becomes the LLM client's internal semaphore: a queue with no depth, no position, no cancel, and nothing an operator can see. `src/job_queue.py` is that queue, made explicit.

It holds **ids and arithmetic only** — no `Job`, no emitter, no persistence — the same split `src/stage_health.py` and `src/retrieval_cache.py` keep, and the reason `tests/test_job_queue.py` can test half of it with no pipeline at all. Two bounds, both read from `jobs` on **every** admission rather than cached, so raising the width in the Configuration tab affects the next admission and not the next restart: `max_concurrent_jobs` (default 2, engine ceiling 8) and `max_queued_jobs` (default 256, engine ceiling 4096). An unreadable value falls back to the default and never widens — a typo must not become the most permissive setting available.

Three rules the callers depend on:

- **FIFO, always.** A queue that reorders is a queue whose reported position is a lie, and the position is the only thing a caller holding a job id can act on.
- **A full backlog is REFUSED, not silently accepted.** Accepting past the bound hands back a job id for a run that may never start, which reads exactly like a run that is merely slow. `QueueFull` carries the depth *and* the limit, and `POST /api/v1/jobs` answers **429** with both — named separately in the UI, or a refusal reads as an outage.
- **Admission is a proposal, not a start.** `release()` returns the ids that may now run; `_start_queued` re-checks `job.status != JobStatus.QUEUED` for each and passes the slot on if the job moved, because hours pass between queueing and a free slot and the run may have been cancelled or paused in between. A job that will not run has to move on, or the backlog drains one short for the rest of the process.

**The width governs SUBMITTED runs only.** A human resuming a paused run, a stage retry, and a link lane's child run all start outside it: each has already been decided or has its own budget, and backpressuring a decision already taken is how a control surface stops being trusted. Which is also why **`release` is idempotent** — a run gives its slot back both when its stage loop exits *and* when it parks on a person (`_release_to_a_human`, guarded on `job.job_id in self.queue.running()`), and the same run does both; releasing an id that holds no slot must free nothing, or a retry would admit a queued job and put the width over. The one non-obvious release is the `skip_stage`-on-the-last-stage branch: it retires the loop by bumping `_run_gen`, so `_run_stages`' `finally` (which releases only under `if job._run_gen == generation`) does not fire and that branch calls `_release_slot` itself.

Four surfaces read the queue, and each needs something the others cannot give: `job_status` announces `queued` with its position and the number in flight (a queued run otherwise renders as the mode line and looks like it started); `GET /api/v1/jobs` returns `{"jobs": [...], "queue": {...}}` with `queue_position` per row; `control()` on a queued job **withdraws** it from the backlog first and records a `dequeued` intervention, because every action on a run that has not started is an operator deciding its fate now; and a restart restores queued jobs as `queued`, which nothing would ever start — `resume_queued()` re-enqueues them oldest-first, stopping at a bound that was lowered between runs and logging what it could not re-admit.

### Batches: a label, not a second record

`POST /api/v1/batches` takes `{"incidents": [...]}` (strings or objects, at most 500 — past that **413**) and creates one job per incident, each carrying `incident["batch_id"]`. That label **is** the batch: no batch record, no batch state, no second copy of a run's progress, so a batch survives export/import and a restart exactly as well as its jobs do and no better. `GET /api/v1/batches/{id}` derives the status from `batch_jobs(id)`; `POST /api/v1/batches/{id}/cancel` cancels each, counting a job that finished between the read and the cancel as `already_finished` rather than as a failure.

Two consequences the tests pin. **Admission is per job and partial by design** — a batch whose tail exceeds the backlog keeps the jobs already accepted and reports the rest under `refused` (with the depth and limit that refused them) or `rejected` (with the index, for an unusable entry), because discarding accepted work to make the response tidy is the one outcome no caller wants. And **`done` is a floor**: `_prune` drops terminal jobs after the TTL, so a batch whose jobs have aged out reports `pruned` instead of letting the arithmetic imply they never ran. An unknown batch id is a 404, not an empty batch.

### Re-entry: a stage list that is not a straight line

Two things make the descriptor list repeat a prefix, and they share one mechanism — `_run_stages` re-entering at an earlier index:

1. **A rejected gate re-runs its own stage** with the reviewer's `guidance` injected, then re-gates.
2. **A declared follow-up pass re-runs `query_generation` + `log_retrieval`** (`_PASS_STAGES`) after the pass-N `log_retrieval` completes *and its gate has been answered* — so an operator holding pass 1 holds pass 2 as well, which is the point. `jobs.max_retrieval_passes` (default 3) bounds it; reaching the cap logs the passes it dropped.

Everything downstream of `log_retrieval` runs **once**, over the accumulated logs. Why passes exist and what a pack declares to get one is in [retrieval.md](retrieval.md#multiple-retrieval-passes--a-question-whose-scope-the-first-retrieval-discovers); what follows is only the runner's side.

**`pass` is a second key, never a composite stage name.** `pass_key(stage, n)` returns the bare stage name at `n == 1`, so `Job.stage_statuses` / `stage_durations` / `stage_summaries` / `stage_health`, the gate config's `stage_gates.stages.*`, `THINKING_STAGES`, an exported job doc and every UI label keep matching a single-pass run exactly as before. `JobContext` carries `current_pass` + `pass_outputs`; `snapshot()["stages"]` entries gain `"pass"` and the snapshot gains `"passes": {"total": N, "current": M}`.

**Control is pass-addressable** — `control(job_id, action, stage, pass=None)`, `resolve_gate(..., pass=None)` and `set_stage_output(..., pass=None)`, where `None` means the current pass so every existing client is unaffected. `retry_stage` on `(log_retrieval, 2)` re-runs that pass only; an override lands in `Job.interventions` with the pass recorded, because a report built on hand-edited data must be traceable to *which* retrieval it edited.

**The UI paginates per section, not per page.** The query-generation, log-retrieval and monitor panels each render their own pass strip, page 1 = pass 1, and with a single pass the strip is absent and the panels render exactly as today. `srcRows` is keyed on `source + "#" + pass`: keyed on source alone, a later pass's query text and row count overwrite an earlier pass's in place, which is the "pass 2 replaced pass 1" failure showing up in the one surface an operator actually reads.
